# Topの共同更新・公開運用ルール

制定：2026年11月26日。重松さん・宮後さん・水金さんと各担当AIの共通手順です。

## 正本と対象

画面の正本は `sunpre-ai/eigyo-no-aibo-Top` のmain、本アプリは固定URLの `/app/` です。画面・JavaScript・CSS・サービスワーカーをTopで管理します。ルートとmockupなどの試験画面を本番と取り違えません。

保存・権限制御のGASは `sunpre-ai/eigyo-no-aibo` の最新mainと同リポジトリの手順に従います。TopにはGASのサーバーコードはありません。公開設定や接続先を過去のメモから推定せず、その時点のファイル・公開設定・実行結果を確認します。

Topの独自変更を保持し、旧GASの生成画面で一括上書きしません。両リポジトリにまたがる変更は、APIの互換性、関連PR、反映順、復旧方法をPRに記載します。画面だけ、GASだけ、両方のどこまで反映したかを区別します。

## マージ前の必須確認

1. 専用ブランチで作業し、担当・対象範囲・関連PRを明記する。
2. `node scripts/check.mjs` を実行する。本番への書込・メール送信はしない。実案件を作らず架空データで確認する。
3. 最新mainを取り込み、他者の変更を保持して差分と全検証を確認する。
4. PR最新コミットのCI `check` が成功していること、未解決の指摘がないこと、現在のmainと整合していることを確認する。
5. 確認した最新SHAを指定してマージする。別のコミットが入ったら、確認をやり直す。

通常修正はAIがこの手順でマージまで担当します。GitHub側の必須レビューや保護設定がある場合は回避しません。本人の依頼が「PRまで」などの場合はその範囲を守ります。

## 公開の順序

既存のPages設定はmainのルートを公開元としています。したがって、**検証済みPRを確認してからmainへマージすることが、公開前の必須段階**です。マージ後に初めて検証する運用にはしません。

流れは「専用ブランチ → ローカル検証 → PRのCI成功 → 最新mainと再照合 → SHA指定のマージ → 既存Pagesの公開成功 → `/app/` の実画面確認」です。ブランチやDraft PRから本アプリへ先に公開しません。

CIは全ブランチとPRで検証を行います。Pagesの自動公開元は変更しません。この手順は、GitHubによる直接push禁止・必須チェック・排他的編集ロックを設定したことを意味しません。担当AIは直接pushせず、成功したPRだけを統合します。

## 確認する表示とデータ

画面変更ではPC・スマートフォン幅の表示、エラー、入力保持、担当別の表示を確認します。認証・金額制限を画面の非表示だけで代用しません。既存の金額制限は営業が自分の担当分まで、原価・採算は管理者だけ、CADには金額非表示を維持します。

PWAの静的ファイル更新では該当キャッシュ版と、既にインストールされた画面の更新方法を確認します。ログイン情報やAPI応答・案件データをサービスワーカーへ保存しません。manifestのid・scope・start_urlは依頼なく変更しません。

実画面は別タブで確認し、入力途中の利用者画面を閉じたり再読み込みしたりしません。試しの本番登録・完了報告・メモ・メール・通知の再送はしません。確認できない場合は、実施済みの検証と未確認の範囲を分けて報告します。

## 通常修正と分ける判断

権限・所有者・認証方式・OAuth・トリガー・保存先・シート/列・データ移行・金額閲覧範囲・URL/公開構成・初回切替は、具体的な影響・順序・復旧方法を示し、人の明示確認を受けます。今回の依頼などで具体的に承認された範囲を繰り返し確認する必要はありません。

## 失敗と復旧

検証に失敗したPRはマージしません。公開が失敗したら、どこまで反映されたかを確認します。コードは確認済みmainからrevert用PRを作り、検証してから戻します。データの復旧はコードと別に扱います。無関係の変更を消したりforce pushしたりしません。

## 完了報告

PR、CI結果、Pages公開結果のURL、対象SHA、変更箇所の操作確認、未確認事項を報告します。権限確認・コード保存・GAS反映・Pages公開・実画面確認は別の事実として扱います。
